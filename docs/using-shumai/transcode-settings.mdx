High-resolution camera formats and raw media files (ProRes, DNxHR, MKV, etc.) cannot be rendered natively in web browsers. Shumai transcodes these assets into web-friendly streaming formats in the background.

---

## Video Transcode Strategies

Team Owners can select how aggressive the transcoding engine should be:

### 1. Best Match (`best_match`)

- **Behavior**: Shumai inspects the container, codecs, and bitrate of the uploaded file.
- **Skip Transcoding**: If the file is already a web-compatible H.264/AAC MP4, WebM, or MOV that browser engines can play directly, transcoding is skipped.
- **Transcode**: If the file format is incompatible, it is transcoded. This is the recommended option as it saves processing time and storage space.

### 2. Transcode All (`all`)

- **Behavior**: Every single uploaded video is forced through the transcoding pipeline.
- **Output**: Converts the file into a standardized, web-optimized H.264/AAC MP4 profile. This ensures consistent streaming performance and compatibility across all client devices and browsers, regardless of the source.

## Transcoding Architecture

Transcoding is highly resource-intensive. Depending on your scaling needs:

- **Local Executor**: Running in local mode, the main application container runs the transcoding task using the local CPU. This is suitable for low-volume uploads.
- **Temporal Executor**: In production, transcoding tasks are offloaded to **Temporal**. You can spin up multiple transcoding worker machines running `@shumai-one/shumai-transcode` (preferably close to your S3 storage server) to process files in parallel.

### System Requirements

Every machine running the transcode process (the main container in Local mode, or the transcode worker in Temporal mode) must have `ffmpeg` and `ffprobe` installed and configured on the system PATH.
